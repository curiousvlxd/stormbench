# 0015. Historian in VictoriaMetrics, runs and alarm journal in PostgreSQL

Status: accepted, 2026-10-17

## Context

Phase 3 compares control algorithms over many runs, not only the running one: the HMI's trend lives in memory and ends with the run (ADR 0010), and alarms are forgotten once acknowledged and cleared. Two kinds of data have to outlive a run. Time series: every control step of a run, with tank levels, setpoints, overflow per point and in total, the inflow to the treatment plant, the Base Case reference, rain, mode, mismatches and alarm counts. Records: one summary per run, so that runs can be listed and compared, and every ISA-18.2 state change of every alarm. Both are written from the UNS host's path, which also carries the lockstep, so a slow or missing store must never hold up a step.

A run of the test console takes seconds to minutes of wall time for 36 hours to a year of model time (ADR 0006). The model time of the Astlingen benchmark is the year 2000.

## Decision

- **Time series in VictoriaMetrics, stamped with model time.** A new feature `Historian/Features/RunSeries` turns every new control step of the current run (Sim01's `Scenario/Step`) into samples at the step's `Scenario/Clock`, and one more set at the end of the window with the final totals. A run is then a time series over its storm window, and runs of the same storm lie on top of each other, which is exactly the comparison Grafana draws. Wall time plus a `sim_time` value was the alternative; it would put runs of the same storm at different places on the time axis and make every comparison a query over a value instead of over time.
- **What model time asks of VictoriaMetrics.** VictoriaMetrics rejects samples older than its retention (default one month): our test instance with the default logged `cannot insert row with too small timestamp 959644800000` for 30 May 2000 and stored nothing. It runs with `-retentionPeriod=100y` ([retention](https://docs.victoriametrics.com/victoriametrics/single-server-victoriametrics/#retention)). Out-of-order samples are accepted, and the query cache assumes current timestamps, so it runs with `-search.disableCache`, as the documentation recommends while samples from the past arrive ([backfilling](https://docs.victoriametrics.com/victoriametrics/single-server-victoriametrics/#backfilling)). Each run has its own label value, so runs never overwrite each other.
- **Names and labels.** `stormbench_step`, `stormbench_rain_intensity_mm_per_hour`, `stormbench_overflow_total_cubic_meters`, `stormbench_basecase_overflow_total_cubic_meters`, `stormbench_overflow_volume_cubic_meters{point}`, `stormbench_wwtp_inflow_cubic_meters`, `stormbench_tank_level_meters{tank}`, `stormbench_valve_setpoint_ratio{valve}`, `stormbench_plc_mode`, `stormbench_shadow_mismatches`, `stormbench_alarms_active`, `stormbench_alarms_unacknowledged`; every series also carries `run`, `storm` and `algorithm`. Volumes are cumulative since the start of the run, as Sim01 reports them. Tank levels and setpoints are the PLC's, as Scada sees them, and only good ones.
- **Prometheus text import.** Samples go as `name{labels} value timestamp_ms` lines to `/api/v1/import/prometheus` ([import](https://docs.victoriametrics.com/victoriametrics/single-server-victoriametrics/#how-to-import-data-in-prometheus-exposition-format)): plain HTTP, human readable, testable as a string, and it carries explicit timestamps, which remote write and OTLP also do but with protobuf and more machinery.
- **Off the hot path.** Every store sits behind a small interface (`ISampleSink`, `IRunStore`, `IAlarmJournalStore`) whose methods only queue. A `BatchWriter` holds a bounded queue (records beyond it are dropped and counted) and one background loop that writes batches; a batch that fails is logged and dropped. Nothing is retried beyond the HTTP client's standard resilience, and nothing waits: the UNS host's work per message is unchanged apart from building the samples.
- **Run summaries and the alarm journal in PostgreSQL 17.** Both are records with a key and a handful of columns, read as tables (the runs list, the journal of one run) and joined (alarms per run); that is SQL's home ground, while a summary in VictoriaMetrics would be a set of series with one sample each. Two plain tables, `runs` and `alarm_journal`, created with `CREATE TABLE IF NOT EXISTS` on startup through Npgsql, no ORM, no TimescaleDB. Model times are `timestamp`, wall times `timestamptz`.
- **One row per run.** `RunRecorder` follows `Scenario/Run` and `Scenario/State` and saves the summary when a run starts and when it finishes, stops or fails: storm and algorithm with their labels, the storm window, started and finished (wall time), steps done and planned, total overflow, Base Case total, change in percent, inflow to the treatment plant, mismatches. The id is the start time and the simulator's run number (`20261017-142530-3`), since the simulator counts from 1 again after a restart. A run whose end Scada did not see is closed as `interrupted`, on the next run or when Scada starts again.
- **Change against the Base Case** is `(overflow - base) / base × 100`, left empty while the Base Case spills less than 1 m³, the same threshold as the KPI tile.
- **Every transition in the journal.** The `AlarmEngine` tells its observers every state change (normal to unacknowledged, acknowledged, returned unacknowledged, back to normal), in order, under its lock; the journal only queues. Each entry has the wall time, the model time of the data that caused it (for an acknowledgement, the model time last seen) and the run current at that moment. The run is passed in as a function, so the Alarms module does not depend on the historian.
- **Read without the HMI.** `GET /api/runs` lists the summaries, newest first; `GET /api/alarms/journal?run=` returns the journal of one run (or the newest entries). Both answer 503 when no database is configured or reachable.
- **Optional.** Without `VictoriaMetrics:Url` and `ConnectionStrings:runs`, Scada runs as before. The HMI's trend of the current run stays in memory: it needs no store and costs no round trip.

## Consequences

- Grafana compares any number of runs of a storm on one time axis, with the Base Case as a reference (ADR 0016). The time range of a dashboard is the storm window in 2000, not "the last hour"; the runs table links each run to its window.
- One step writes about 30 samples; the rain year (105,406 steps) about three million, which VictoriaMetrics stores without effort. The journal grows by a few rows per alarm.
- With `-search.disableCache` every query is computed afresh. For the data of a testbed that costs nothing measurable; a historian of a real plant, written in wall time, would keep the cache.
- The format, the sampling, the run summaries and the journal are unit tested; the stores are tested against PostgreSQL 17 and VictoriaMetrics in Testcontainers, including a read back of samples from May 2000.
- If PostgreSQL or VictoriaMetrics is down, what happens meanwhile is lost, and the log says how much. The lockstep and the HMI are not affected.
